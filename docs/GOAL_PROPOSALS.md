# Оконные цели:0.9

Реализован ОДИН предлагаемый шаг, не многошаговый автопилот. Выбор окна → цель → локальная модель → типизированное предложение → пользователь подтверждает → свежая проверка окна/элемента → исполнитель → проверка результата. Без подтверждения эффектов нет.

src/core/action_proposal.gd ограничивает наблюдение24контролами/2200байтами, выдаёт opaqueID, строит action-specific anyOf schema. Никаких произвольных shell/координат/инструментов отLLM. Написание текста только вербатим из цели, максимум256символов; существующее поле защищено старым ValuePattern-гейтом. Invokeкнопки доступен модели только при явном глаголе нажатия и буквальном имени кнопки в цели. Отрицательные и неинтерфейсные запросы отсекаются до модели. Контекст выбранного окна иUIJSON не попадают в диалоговые turns.

App.goal_mode:loading/observing/thinking/proposal/confirming/executing/verifying. Модель запускается ДО наблюдения, один общий worker. Планирование до90сек по snapshot, подтверждение15сек после ответа; перед исполнением делается новый snapshot, проверяются HWND+PID+StartTime/названиеокна/runtimeID/name/capability. select/expand дополнительно проверяются по selected/expansion свежего snapshot. Invokeподтверждает лишь вызов кнопки, не бизнес-итог задачи. Очистка/сменаокна/пауза/отмена/ошибка уничтожают право позднегоисполнения. Черновик не теряется при занятом помощнике.

В исходном тесте маленькая модель предложила Delete на просьбу о шутке. Эффектов не было. Исправлено ограничением разрешённых capabilities ДО генерации и отсеиванием нерелевантных задач. Не выдавать shape-correct JSON за семантическую надёжность. Реальные тесты: RUвыборInsert,ENвводhelloвSearch,ZHвыборInsert;19–28сек наCPU2threads в этой среде. Требуются ускорение и больший корпус; Windows UIAвживую не проверен. Набор38checks включает только3realmodelкейса идетерминированные проверки; не38реальныхпрограмм.
