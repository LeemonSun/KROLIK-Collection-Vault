# Leemon 0.18 — цельное поведение настольного персонажа

Этот проход улучшает постановку прежнего Лимона и исправляет конкретные ошибки жизненного цикла. Не улучшает общую логику модели и не завершает универсальный агент. Модель, лицензии, разрешения на действия и формат данных сохранены. Новые художественные ассеты не добавлены.

## Механизмы

- `src/desktop/locomotion.gd`: чистый time-sampled маршрут, 140 мс подготовки, quintic ease с нулевой скоростью на концах. Длительность зависит от расстояния; скорость пика по умолчанию 180px/s, масштабируется пользовательским размером. Малые перемещения менее8px игнорируются. Накопленный путь связывает шаги с фактическим перемещением; нет обхода препятствий или физики всех окон.
- `companion_window.gd`: состояния task > временная реакция > idle, а drag/маршрут имеют собственный приоритет. Короткие реакции ограничены временем/приоритетом; после завершения снова выбирается настоящая активность. Это устраняет зависание рабочей позы после временного жеста. Синхронизация задач раз в150мс; моделей/захвата экрана в цикле анимации нет.
- Захват мышью немедленно отменяет маршрут. Потеря фокуса освобождает захват; пауза, reduced motion, resize, restore и сворачивание сбрасывают старое движение. В reduced motion сохраняется текущая позиция, без позднего прыжка к старой цели. Явное новое `walk_to` в reduced mode может мгновенно установить выбранную позицию; автоматическое парковочное движение отключено.
- `app.gd`: после паузы восстанавливается настройка `companion_roam`, которая раньше оставалась false. Ответы вызывают контролируемую реакцию вместо прямого произвольного `art.play`.
- `leemon_rig.gd`: внешнее управление фазой ног от пути; наклон по направлению без зеркального отражения исходного рисунка. Это фронтальная процедурная походка, не нарисованный боковой walk cycle. Скрытый/уменьшенный rig не выполняет `_process`; после восстановления обработка возвращается. Генерация hit envelope сохраняет текущую позу и параметры gait без нейтральной вспышки.
- `speech_bubble.gd`: окно реплики следует за видимым персонажем не чаще10Гц; выбирает ограниченную экраном позицию слева/справа/сверху/снизу. При наличии места персонаж не закрывается. На очень маленьком экране непересекающаяся позиция может отсутствовать. Открытие чата/пауза/скрытие останавливают сопровождение. Реплики — существующие реальные сообщения/стадии, дополнительного LLM-запроса нет.
- Персонаж не начинает бесцельно бегать и не считывает окна самовольно ради анимации. Автопарковка по геометрии чата и явно выбранной цели сохранена. Путь не обещает обход всего содержимого экрана.

## Проверки и ограничения

`tests/test_locomotion018.gd`:76проверок физического предела скорости/точного конца/отрицательных координат/15–144fps/одинакового положения при одинаковом времени/отмены/invalid delta/реплик/гейта обработки/сохранения позы при envelope. Это синтетическая кинематика, не замер производительности Windows.

`tests/test_performance_visual018.gd`:33проверки реальных X11-окон с синтетическими задачами: приоритет работы, истечение реакций, реальное перемещение host, хватание мышью, пауза/возврат настройки, reduced mode, регион ввода, следование реплики, сворачивание/возврат.

`tests/test_desktop_visual.gd`:156проверок PASS. Каталог низкоуровневых поз изолирован от нового task-арбитра на время прямых обращений `art.play`; интеграция арбитра проверяется отдельно, не обходится в product code.

Прочие проверки исходников/пакета — `reports/VALIDATION.md`, session. Семантические провалы0.17сохранены; программный PASS не означает улучшение интеллекта. Windows, DPI, native UIA, несколько физических мониторов, реальная нагрузка рядом с игрой и качество системного голоса ещё не проверены. Режим малого ресурса — программная политика, не жёсткая OS quota.

`tools/capture_motion018.gd`: сценарная демонстрация настоящего renderer с синтетическими стадиями. Нет модельного вывода, реальных действий на ПК или замера FPS. Видео монтируется20fps из180кадров; не выдавать это за аппаратный benchmark.

## Следующий технический проход

1. Приёмка018на реальной Windows: перетаскивание, input passthrough, alt-tab/tray, сон/возобновление, DPI100/150/200%, мониторы с отрицательными координатами; замеры idle/work/game.
2. Общий интеллект остаётся главным препятствием. Сравнить компактные instruction-модели/форматы наблюдения на одинаковых24case RU/EN/zh с ручной оценкой смысла и фактов, до добавления новых крупных весов по умолчанию.
3. Общие UIA role/type адаптеры и честное восстановление после изменения интерфейса; результат подтверждать наблюдением. Не писать отдельную модель на каждое приложение.
4. Связать ответы с источниками выбранного окна/файла/страницы. Расширять Office/WPS через проверенные операции, не изображать поддержку любого редактора.
5. Художественный этап: раздельные оригинальные детали лица/очков/рта/листа/костюма и полноценные выразительные клипы. Текущие26состояний — не сотни рисованных анимаций. Нового персонажа вместо Лимона не вводить.
