# Leemon0.17 — separate authoring from UI planning

Explicit composition request in a pinned window: fresh observation→eligible field selection→plain-text authoring→independent validation→full preview→approval→fresh native preflight→write/readback. If one supported writable field exists, or exactly one observed field is explicitly named, field selection does not require a model request. Ambiguous fields use a choice-only model step before plain authoring. Field references such as “in Body”, “в поле Body”, “填入Body” are removed from the authoring request so a UI label is not treated as a meeting location. Original goal/context remains for authority validation. Control/window labels are not sent as authoring instructions. No send/invoke, overwrite or arbitrary effect authority is added. Existing literal entry unaffected.

New capability_answers.gd answers a narrow set of capability questions from actual ToolPolicy, without inferring host capabilities from model guesses. General conversation stays with LLM. Three locales; repeated queries cause no effects or hidden history writes.

Provider now reports total/template/tokenization/prompt/decode/cache metrics separately. Developer diagnostics displays numeric measurements, not prompt or private reasoning text. Optional explicit reasoning_tokens=128 protocol is supported only for owned authenticated text requests; schema/vision requests disable it. No automatic reasoning mode is enabled: actual2B bounded reasoning did not reliably solve the pilot logic task and cost more tokens/time. Template preflight and generation must use matching thinking kwargs, reserve total128extra tokens, cap512overall. Raw reasoning_content is never emitted or retained in metrics.

Development benchmark: tests/export_benchmark017.gd exports fixed synthetic3locale logic/draft cases, tools/benchmark017.py uses owned pinned runtime/model, per-case receipts and prompt/decode timings.2B baseline and128reasoning pilot complete in reports/benchmark017-ab.json. Manual reading shows liar-paradox errors in all baseline languages and no reliable correction with bounded thinking; relative-time invitation prompts alone were correct in3languages. These are exploratory samples, not a broad IQ benchmark. Baseline and thinking costs differ; do not enable failed modes or claim speedup from small/contended samples. Initial RSS sampler returned0 due namespace mapping; treat unavailable, NOT zero memory. Sampler mapping subsequently fixed.4B candidate downloaded outside repository for dev comparison only, not bundled/integrated/default.

First actual App+2B plain composer trial was not a semantic success: RU added “today evening”, EN treated Body as a location, zh failed.23synthetic composer checks pass after destination separation; real rerun still needed. Record failures; do not infer success from a relevant keyword. Windows acceptance still pending.

## Final content safeguards and limits

Grounding now recognizes a small canonical set of relative day/daypart words acrossRU/EN/zh, including word-number Chinese clock expressions; equivalents such as tomorrow/завтра/明天 are allowed. It is NOT an NER or arbitrary factual validator and can reject legitimate date conversions. One failed supported detail check supplies concrete witnesses to one bounded corrective authoring request; maximum2authoring attempts, same window authority/time budget, no invalid draft displayed or saved as a conversation turn. The existing freshness/preflight gates remain; a slow task can still expire. No same-model semantic critic is enabled.

Actual 2B rerun after revised author prompt: all3 produced review proposals; EN clean invitation, RU invented an office (not caught by narrow gate), zh omitted explicit meeting object. Automated semantic test18checks/1failure and manualRUissue remain limitations; do NOT claim universal draft correctness. Final safeguards/cancellation tested separately with synthetic witnesses. Reports keep prior failed and final real outputs.4Bpilot improved EN liar-paradox explanation, but RU began with a wrong false assertion and zh reasoning also imperfect. It is a dev candidate, not a new production brain. Vendor-recommended2B sampling pilot degraded this task set, so production sampling was retained.

Developer diagnostics separates request phases, reports partial process metrics, and no longer falls back to an unrelated hostPID when namespace mapping fails. Earlier standalone benchmark RSS values were invalidated; later vendor run uses kernelRUSAGE_CHILDREN after owned worker exit (~2.35GB worker peak in Linux, not Windows/app-total). This is a sample, not a minimumRAM requirement or hard quota.
