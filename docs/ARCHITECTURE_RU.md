# Архитектура KROLIK Collection Vault

## Основной принцип

Vault хранит исходные изображения отдельно от сцены. Ячейка не является заранее склеенным растром: архитектура, процедурная конструкция, дополнительные объекты, персонаж, передний план, атмосфера и подписи существуют независимо.

## Слои сцены

1. Архитектурный фон Vault.
2. Корпус ячейки и задняя часть базовой конструкции.
3. Задние части дополнительных объектов.
4. Персонаж.
5. Передние части дополнительных объектов.
6. Передняя часть базовой конструкции.
7. Свет, туман, пыль и интерфейсные выделения.
8. Подпись ячейки.

Такой порядок позволяет помещать персонажа внутрь бочки, капсулы, клетки, кольца или другой конструкции без перерисовки исходника. Объект сам рисует заднюю и переднюю части, поэтому часть изображения естественно скрывается передним слоем.

## Scene Object Engine

Дополнительные объекты хранятся в SQLite в таблице `props`. Каждый объект имеет:

- ячейку;
- тип;
- положение X/Y в нормализованных координатах;
- ширину и высоту;
- поворот;
- глубину;
- прозрачность;
- JSON параметров;
- блокировку.

Встроенная процедурная библиотека сейчас включает узкую и широкую бочку, стеклянную капсулу, коллекционную раму, портальное кольцо, каменный пьедестал, внутреннюю клетку и коллекционный ящик. Она не требует интернет-текстур.

## Interaction / Spring binding

Размещение персонажа может быть привязано к объекту. Хранятся:

- ID объекта;
- точка привязки: top/center/bottom/left/right;
- точка вращения изображения `pivot_y`;
- глубина посадки;
- амплитуда движения;
- вертикальное покачивание;
- упругость;
- затухание;
- мягкая сегментная деформация силуэта без изменения исходного файла.

Во время рендера используется локальная пружинная модель. Поэтому персонаж может быть закреплён относительно проёма объекта, следовать за объектом при его перемещении и получать затухающую реакцию на импульс. Это не меняет оригинальное изображение.

## Данные и миграции

`SCHEMA_VERSION = 11`. Старые проекты мигрируют вперёд при запуске: добавляются атмосфера ячейки, таблица объектов и поля привязки размещения. Оригиналы не переписываются миграцией.

## Scene Timeline

`scene_clips` хранит неразрушающие клипы конкретной ячейки. Ключевые кадры содержат снимок трансформации размещения, трансформации всех объектов и параметров атмосферы. Runtime интерполирует кадры только при рендере, поэтому воспроизведение не записывает промежуточные координаты обратно в SQLite. Ограничение в 200 ключевых кадров и 512 КБ JSON на клип защищает проект от случайно чрезмерного состояния.

## Scene Templates

`scene_templates` хранит переносимое устройство ячейки без изображения персонажа. Шаблон включает `fixture_type`, `ambience_json`, объекты `props` и индекс объекта, к которому было привязано размещение. При применении создаются новые ID объектов, после чего привязка существующего персонажа безопасно переназначается на соответствующий новый объект. Заблокированные объекты не заменяются автоматически.

## Масштабирование

- Canvas виртуализирует ячейки по видимой области.
- Изображения имеют уровни 256 / 768 / original.
- LRU-кэш ограничивает количество декодированных изображений.
- Мир расширяется этажами без фиксированного потолка в 96 ячеек.
- SQLite работает в WAL-режиме.

## Надёжность

- автоматические и ручные бэкапы;
- консистентный снимок SQLite при ZIP-экспорте;
- SHA-256 дедупликация изображений;
- блокировки персонажа, размещения, ячейки и объекта;
- undo/redo трансформаций персонажа и объектов;
- диагностика потерянных файлов и целостности БД.

## Следующие архитектурные уровни

Текущий Scene Object Engine специально сделан базой для дальнейшего 2D rig: сегментации изображения, деформируемой mesh-сетки, костей, IK и независимой вторичной физики волос/одежды/частей силуэта. Эти системы должны подключаться к существующим `poses`, `camera_profiles`, `props` и `interaction_json`, а не заменять текущий формат проекта.
