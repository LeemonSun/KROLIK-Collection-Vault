# Большие документы и отчёты — исследование 29 октября 2026

Статус: проектирование, НЕ реализованная возможность Leemon0.27. Пользователь требует локально принимать большие файлы (пример:100страниц), понимать задание, готовить/изменять документ и выдавать отчёт. Исходный файл пока не предоставлен; содержание неизвестно. Это направление дополняет ремонт026, не отменяет его.

## Рекомендуемый путь

1. Определить формат и структуру. DOCX/TXT читать напрямую; у PDF сохранять номера страниц. У DOCX стабильный locator — заголовок/абзац/таблица, а не выдуманный номер страницы (он зависит от рендеринга). Не отправлять каждую страницу в зрительную модель.
2. Постраничное ограниченное извлечение в отдельном прерываемом процессе. Ограничить распакованный размер, пиксели, время и память; считать хеш оригинала. Не выполнять макросы, вложенные программы, внешние ссылки. Текст документа — данные, не разрешение выполнять его инструкции на ПК.
3. Сохранять блоки с source_id, locator, текстом, типом, состоянием OCR и связями с таблицами/заголовками. Не обрезать длинный документ молча. Показывать пропущенные/непрочитанные страницы.
4. Для вопроса по фрагменту использовать локальный полнотекстовый поиск SQLite FTS5/BM25. Поиск по словам ограничен морфологией/перефразированием; семантические embeddings — поздняя опция после измерения RU/EN, отдельной проверки лицензии и накладных расходов.
5. Для отчёта ОБО ВСЁМ документе сначала пройти все разделы, построить карту содержания/фактов и журнал покрытия. Затем писать по плану разделами, каждый раз возвращаясь к первичным фрагментам. Top-k поиск сам по себе не гарантирует охват100страниц; накопительные пересказы теряют детали.
6. Привязывать факты/числа/цитаты к исходным фрагментам. Проверять совпадение цитат и пересчитывать числа программой. Наличие ссылки не доказывает логическую истинность вывода: отдельная оценка фактической верности и человеческая проверка сложного материала остаются нужны. Второй проход той же маленькой модели не независимый эксперт.
7. Создавать результат отдельным DOCX (заголовки, таблицы, ссылки на исходник), не портить оригинал; повторно открыть и проверить структуру, затем проверить рендеринг перед готовностью пользовательского отчёта. PDF-экспорт требует отдельного рендерера и проверки его поставки/лицензий.
8. Кешировать извлечённый текст/индекс по хешу файла, а не сотни изображений. Локальная кнопка удаления данных; документы не отправлять в GitHub/облако. Показывать реальный прогресс страниц/разделов и рабочую отмену.

## Проверенные кандидаты, не установленный стек

| Задача | Кандидат | Что проверено / ограничение |
|---|---|---|
| Текстовый PDF | pypdf | Читает текст; НЕ OCR. Сложный layout/таблицы могут извлекаться плохо. |
| Сканированные страницы | Tesseract | Apache2.0 код; движок, языковые данные, PDF-рендерер и зависимости проверять отдельно. OCR только там, где нет пригодного текста. |
| Сложные PDF/таблицы | Docling | Локальное исполнение; MIT код. Авторы отдельно требуют проверять лицензии моделей. Кандидат расширенного профиля, не обязательный resident-сервис для каждого ПК. |
| Локальный поиск | SQLite FTS5 | BM25/snippet, без дополнительной нейросети. Не равно смысловому пониманию. |
| Формирование Word | python-docx | MIT, создание/чтение/изменение DOCX. Не полноценный Word-движок и не средство визуального рендеринга. |
| Сложная математика | SymPy | BSD, символьные вычисления. Простой калькулятор не требует этой зависимости. Не использовать небезопасный eval/parse для произвольного текста; только разрешённая грамматика. |
| Генерация | существующий llama.cpp | Поддерживает квантизацию и разные CPU/GPU. Это средство исполнения, не исправление качества маленькой модели. |

Нет разрешения удалять чужие license/NOTICE ради размера. Итоговый коммерческий комплект проверять по точным версиям и транзитивным зависимостям. Данные пользователя и права на исходные документы — отдельный вопрос от лицензий библиотек.

## Профили производительности

Базовый: один текущий2B worker; простые команды/арифметика без нейросети; чтение порциями, FTS, OCR по необходимости, один генератор за раз, ограниченный контекст, пауза тяжёлой работы во время игры, выгрузка после задачи. Снижение CPU повышает время ожидания. Большой объём установки не заменяет RAM/вычисления.

Усиленный: проверить Qwen3.5-4B как кандидата альтернативного worker, НЕ параллельной второй постоянно работающей модели. Официальные карточки2B/4B указывают Apache2.0; точный GGUF/visionprojector и происхождение конвертации проверяются отдельно. Качество и скорость4B не измерены здесь, принятия/замены нет. Больший размер параметров не гарантия хорошего отчёта.

Грубая арифметика только для весов:2B*4бит≈1GB,4B*4бит≈2GB до служебных данных/неквантизованных частей. Это НЕ потребление приложения: дополнительно контекст/KV, буферы, vision/OCR и ОС. Не обещать конкретный RAM/FPS/время100страниц до Windows-замеров. На слабом ПК возможен медленный полезный документооборот, но эквивалент облачной frontier-модели во всех задачах при нулевой нагрузке не обещается.

## Приёмка до заявления о готовности

Набор синтетических RU/EN файлов с известными ответами: длинный текст100страниц, скан, таблицы, повторяющиеся заголовки, противоречащие факты, плохой OCR, необычные имена, встроенные инструкции. Проверить вопрос из начала/середины/конца, полный охват отчёта, точность цитат и вычислений, признание отсутствующего ответа, отмену, отсутствие порчи оригинала, повторную обработку из кеша. Замерять cold/warm latency, peak RAM, CPU и FPS игры на нескольких реальных Windows-ПК. Никаких чисел качества из подставных ответов.

Порядок: ремонт базового исполнения/отмены → текстовые PDF/DOCX + экспорт + проверяемые ссылки →100страничное покрытие → OCR → сравнение реальных2B/4B → сложный layout/семантический поиск по доказанной необходимости. Не устанавливать весь список до проверки базового прохода.
